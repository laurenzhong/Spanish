# ADR-0009：版本化角色运行时与对话闭环边界

- 日期：2026-09-26
- 状态：Accepted（产品本人批准将该方向写入实施计划；阶段 0–1 基础切片已实现并待验收，阶段 2–4 尚未开始）
- 任务：`CONV-ROLE-001`

## 背景

当前对话系统已经具备流式消息、角色目录、关系记忆和多个 provider adapter，但“角色”仍同时由静态目录、人物 JSON、数据库记录和角色 key 分支描述。Lucía 拥有完整的人物设计，而 Mateo/Inés 只有简化的 prompt snapshot。若继续把所有可调用模型的名字都作为正式角色，会产生以下风险：

- 草稿人物可以通过 UI、历史或直接 API 被当作可聊天角色；
- Mateo/Inés 可能继承 Lucía 的恋爱、主动消息、时区和关系逻辑；
- provider 输出可能伪造人物事实、升级关系或写入未经允许的记忆；
- 角色关系阶段和上下文在不同角色之间回落或串用；
- 流重试、删除/撤回和语音输入尚未形成可验证的完整回合。

## 决策

### 1. 角色是版本化的发布单元

每个长期角色必须拥有版本化人物包、固定事实、透露策略、关系/记忆 policy、现实边界、capability policy 和 replay/evaluation manifest。生产请求只接受 `published` 版本；`draft` 和 `retired` 角色不进入正式联系人目录，所有新建/发送/关系接受 API 也必须 fail closed。已有用户拥有的旧版本会话只允许经过所有权和版本检查后只读恢复，不能静默删除历史。

### 2. 生命周期与能力独立建模

角色生命周期（`draft`/`published`/`retired`）与能力（basic/full、主动消息、语音、恋爱暗示、私密记忆、介绍）分别存储和校验。角色行为不再由 provider 或散落的 `characterKey` 条件决定。

### 3. Alpha 只正式开放 Lucía

Lucía 是唯一可以承载完整长期关系的 Alpha 角色。Mateo/Inés 在独立人物包、审核、发布和回放集完成前保持 draft/coming-soon；若未来开放，先使用没有主动消息和恋爱分支的 `basic` policy。场景练习的临时人物继续由 `scenario-practice` 拥有，永不进入长期角色表或关系记忆。

### 4. 服务端生成统一角色运行时上下文

`characters` 模块拥有人物版本与固定事实；`memory` 模块拥有用户与角色的关系记忆及共享权限；`conversation` application 读取当前已发布版本、角色 policy、当前用户关系快照、可读记忆和最近完成消息，组装 provider-neutral `CharacterRuntimeContext`。provider adapter 不直接访问数据库，也不能写人物、关系或记忆事实。

### 5. 完整回合是派生状态的唯一触发点

只有通过 `done`、Schema、安全门禁和幂等校验的完整回合，才能更新关系事件候选、开放话题、摘要和长期记忆。旧 generation、取消、断流、删除/撤回和技术失败不得产生角色事实、关系升级、学习证据或隐藏的 fallback 回复。生产环境缺少数据库权限来源或真实 provider 时返回可恢复错误，不运行 deterministic fake。

### 6. 场景人物与长期角色隔离

临时人物只存在于场景会话快照中，不创建长期会话、联系人、关系记忆或角色目录条目。角色对话和场景练习的 provider 入口、数据表和测试基线保持清晰边界。

## 备选方案

### 方案 A：继续把三角色都作为通用 AI（不采用）

实现最快，但无法保证事实、关系、隐私和行为一致性，也会让 UI 对草稿状态作出错误承诺。

### 方案 B：立即为 Mateo/Inés 完成完整人物圣经

可以较早提供多角色体验，但扩大人物内容、评测和隐私表面积，会延迟 Lucía 和对话可靠性收口。当前 Alpha 没有足够理由同时承担这项成本。

### 方案 C：Lucía 完整角色 + Mateo/Inés basic（分阶段采用）

先完成 Lucía 和通用运行时边界；在产品确认有多角色需求后，为 Mateo/Inés 分别提供受限 `basic` 包。这保留扩展路径，同时不让临时 prompt 冒充长期角色。

## 后果

正面后果：

- 角色发布、关系权限和 provider 行为有单一服务端边界；
- 可以独立评测和版本化每个角色；
- 失败、重试、撤回和记忆派生的语义更容易测试；
- 新角色不会自动继承 Lucía 的情感或主动消息逻辑。

成本与限制：

- Lucía 发布前需要解决人物资料冲突并完成回放/人工验收；
- Mateo/Inés 暂时不能作为完整联系人；
- 需要增加 runtime policy、版本引用、关系读取和跨角色契约测试；
- 当前先不引入复杂检索、消息队列或实时通话。

## 迁移与验收

实施按 `docs/plans/2026-09-26-character-runtime-and-conversation-closure-implementation-plan.md` 分阶段进行。每阶段必须保持现有人物版本、消息、关系记忆和学习证据可追溯；不得静默发布草稿或覆盖已有角色版本。发布前至少通过角色状态门禁、stream 幂等/竞态、删除撤回隐私、关系隔离、provider replay、桌面/移动关键路径和人工 Lucía 体验验收。
