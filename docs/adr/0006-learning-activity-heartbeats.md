# ADR-0006：服务端活动心跳计算有效学习时长

- 日期：2026-08-25
- 状态：Accepted

## 背景

热力图要求表示有效学习时长，必须排除页面空置、浏览器后台挂起、App 后台和长时间无交互。仅用练习会话的 `started_at`/`completed_at` 无法区分这些状态，也会把客户端时钟或网络恢复后的整段时间误算为学习。

## 决定

1. 在 `practice_session_activity_events` 保存服务端接收的 `active`、`inactive`、`ended` 事件。
2. 使用 `(session_id, client_instance_id, sequence)` 幂等约束，客户端重试不会重复事实。
3. 服务端领域函数只计算同一客户端实例中相邻 `active` 事件的间隔；间隔超过 45 秒、生命周期暂停和未收到下一次心跳的尾部不计入。
4. 单会话有效秒数封顶 45 分钟，热力图再按天向上取整为分钟。
5. Web 和 Flutter 通过各自生命周期适配器发送同一协议；采集失败不阻塞训练，也不本地补造过去时长。
6. 没有活动事件的旧会话按 0 分钟处理，不从历史起止时间反推精确有效时长。

## 替代方案

- 客户端直接上报有效秒数：无法验证前台状态，容易被时钟、后台挂起或篡改污染。
- 只在 `practice_sessions` 增加 `active_seconds`：失去事件审计、幂等重试和跨端生命周期边界，且难以修正算法。
- 浏览器埋点或第三方遥测：会扩大隐私和供应商边界，不符合个人 Alpha 的最小数据范围。

## 后果

服务端增加活动事件写入和读取成本，且突然退出前的最后一段可能被保守地少算。换取的好处是热力图不把空置或后台挂起误报为学习，并保持掌握度/可信度完全不受时长影响。活动表属于训练数据，跟随用户和会话删除级联清理；不保存输入正文、音频、转写或设备指纹。
