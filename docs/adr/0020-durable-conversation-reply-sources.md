# ADR-0020：整批聊天回复的持久来源关联

- 日期：2026-10-17
- 状态：接受，随 `CHAT-RHYTHM-001` 实现
- 范围：conversation模块内部数据与隐私边界；不改变NDJSON v1和角色记忆共享权限

## 背景

连续用户消息现在由一个逻辑角色回复共同回应。原有 `messages.reply_to_message_id` 只能关联最新一条用户消息，不能表示整批来源。仅在HTTP请求生命周期保存较早来源ID，会导致两个可复现问题：撤回/删除较早来源后，已保存的角色回复仍能在历史/搜索中出现；同一个generation重试时可以删减或重排原批次而不被识别为冲突。进程内数组不能提供持久的隐私和幂等保证。

## 决定

新增conversation拥有的 `conversation_reply_sources` 关联表，保存助手消息ID、来源用户消息ID、用户/会话作用域和批次位置。助手与来源各有级联外键，助手/来源复合主键保证唯一，助手/位置唯一约束保留顺序；按来源建立查询索引。表启用RLS，仅允许authenticated读取属于自己的关联，不授予客户端写权限；服务端在短会话事务内校验角色、用户、会话、消息状态和完整批次。

claim事务同时保存独立用户消息、助手占位和有序来源。已存在generation必须精确匹配原有序批次；前缀保存与完成使用持久来源重检，不能信任调用者省略的来源列表。迁移0047只将可信的旧replyTo关系转为单来源关联，不从历史推断更多成员或回填不存在的批次。

撤回或删除一条来源时，同事务仅删除直接依赖该来源的助手消息，并保留该generation的空取消标记，防止晚到回调或重试复活已清理回复。关联行随外键级联清理，已有记忆按来源删除的规则继续执行。无关用户、角色及其他轮次保留。空取消标记不进入历史显示、搜索、上下文和记忆。

## 替代方案

- 只保存最新replyTo：无法表达整批来源，回归已证明隐私和幂等缺口。
- 请求内数组或进程内Map：刷新、重启、跨请求与已完成回复均失去关联。
- 把来源ID编码进sourceType/generationId或隐藏消息正文：混淆字段语义，难以执行外键、RLS和精准撤回。
- 删除某时间段之后的全部回复：无法证明它们依赖被撤回来源，会损坏无关轮次。

## 后果

新增一项版本化数据库迁移；必须在使用新来源路径前应用，不能以代码发布替代迁移，也不通过手工DDL绕过迁移追踪。只新增结构，不改写既有聊天正文或人物设定。PGlite覆盖有序幂等、来源撤回/删除、完成与取消前缀、跨用户所有权、RLS和撤回后重试拒绝；目标数据库的迁移状态和权限需另外验证，不能从隔离测试推断已上线。

这份来源表是回复直接依赖的审计边界，不宣称能从任意后续自然语言中清除所有间接提及；长期记忆仍由memory模块按已完成轮次、规则及权限管理。
