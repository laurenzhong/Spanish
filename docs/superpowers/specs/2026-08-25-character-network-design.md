# 好友介绍与角色网络设计（ALPHA-030）

## 背景

Lucía 好友系统已经支持人物圣经、单角色关系记忆和显式共享权限。ALPHA-030 在此基础上增加两个可被介绍的角色，并让介绍、用户同意、联系人创建和最小资料共享成为一个可幂等重试的服务端流程。

## 范围与不变量

- 只创建一个兴趣好友和一个生活关系角色；不实现开放角色商城或大规模网络。
- Lucía 只有在最近对话或内容事件提供真实上下文理由时才可提出介绍。
- 提议必须经过用户明确接受；拒绝、撤回或过期提议不得创建联系人。
- 接受时只共享用户明确选择且通过所有权、敏感级别和目标角色校验的最小资料；默认不共享私密记忆。
- 每个角色独立拥有 `character_relationships`、关系阶段、已揭示人物事实和可读关系记忆；介绍不会把教学画像或其他角色私密记忆带入新角色。
- 接受操作和关系创建必须幂等，重试不能重复创建关系、会话或共享授权。

## 设计

### 领域与 application

`character-network` 领域提供纯函数：根据最近消息、内容事件和可用角色关系判断介绍理由，生成稳定的提议 ID，并校验接受/拒绝状态转换。application 层依赖角色目录、提议仓库和关系仓库，通过事务完成接受：锁定 pending 提议，校验用户选择的资料，创建目标角色关系和会话联系人，再写入显式共享权限。

介绍理由只允许可解释的事件类型（共同兴趣、当前内容包中的角色关联、用户明确表达的生活需求）；没有理由时返回 `no-offer`，不生成教学化或随机介绍。

### 数据与 API

新增版本化 `character_introduction_offers` 表保存用户、来源角色、目标角色、理由、状态、过期时间和幂等键。现有 `character_relationships` 作为联系人/关系权威表；现有 `conversations` 通过唯一用户-角色约束提供会话联系人。接受接口接收用户选择的 memory IDs，服务端通过现有 memory repository 验证所有权与可分享范围，并为目标角色写入显式权限。

Web API 提供读取当前待处理提议、接受和拒绝操作。错误使用稳定代码区分未登录、提议不存在/已处理、角色不可用、资料不可共享和数据库不可用。

### 人物

兴趣好友和生活关系角色以版本化人物圣经保存，初始为 `draft`，不绕过审核发布门禁。其固定事实、揭示策略和关系网络与 Lucía 分离。

### 测试

- 领域：无理由不提议、合法理由提议、状态机非法转换、稳定提议 ID。
- application：拒绝不创建、接受创建独立关系、最小资料共享、重复接受幂等、冲突/过期提议拒绝。
- 数据库：用户隔离、角色关系唯一性、共享权限只对目标角色生效、私密记忆不可读。
- API/UI：未登录和稳定错误码、接受/拒绝反馈及刷新后状态一致。

## 明确不做

不实现角色商城、自动跨角色共享、实时双向语音、推荐图谱、进步展示或独立微服务。
