# 对话连续性与关系上下文设计

- 状态：待产品确认
- 日期：2026-08-29
- 范围：ALPHA-033，Lucía 对话连续性第一阶段

## 1. 背景与问题

当前对话流已经把用户消息和角色消息持久化到 PostgreSQL，也会在生成回复前读取最近 20 条完成消息，并将人物设定、可读关系记忆、问题预算和当前用户消息传给 provider。

这并不等于角色拥有稳定的上下文能力，原因有四个：

1. provider 只看到固定长度的近期原文，较早但仍有价值的话题会消失。
2. 原文没有明确表达“哪些问题已经问过并回答、哪些事项仍未完成”，模型可能重复问相同问题或复用相同答案。
3. 普通聊天 route 尚未把 Lucía 的真实关系阶段和关系摘要传给 `buildReplyContext`，因此会落到 `new_contact`/`null` 默认值。
4. 关系事件、用户边界和最近互动节奏没有形成独立的 provider-neutral 上下文层，provider 需要从原始对话自行推断关系状态。

用户观察到的“中午吃什么”重复提问和无变化回答，正是上述问题的典型表现。它可能还会叠加历史竞态产生的重复记录，但不能只靠清理历史或增加提示词解决。

## 2. 目标

- 每个完整对话轮继续作为权威事实持久化。
- 每次生成都能稳定获得当前话题、近期语气、关系阶段和用户边界。
- 已回答的问题不会被机械地重复；旧话题重新出现时可以自然换角度延续。
- provider 更换只主要影响措辞、长度和语气，不改变关系事实、记忆权限和行为边界。
- 上下文构建保持在服务端 application/domain 层，provider adapter 只接收统一 DTO。
- 不把感情压缩成单一分数，不让模型直接写入人物圣经、关系记忆或关系阶段。

## 3. 非目标

本设计不包含：

- 无限长度原文每轮完整发送给 provider；
- 向量数据库或复杂语义检索；
- 本地训练或微调模型；
- Web Push、APNs、FCM 调度；
- 自动把模型输出直接写入关系事实；
- 为 Mateo、Inés 等其他角色开启 Lucía 的私密关系记忆。

## 4. 方案比较

### 方案 A：每轮发送完整历史

优点是实现直观，短期内能看到更多原始细节。缺点是 token、延迟和费用随对话增长；不同 provider 的上下文窗口不同；旧信息会淹没当前话题；隐私过滤、撤回消息排除和上下文注入控制更困难。它不能保证模型理解哪些内容已经结束，因此不是推荐方案。

### 方案 B：近期原文 + 滚动摘要 + 结构化关系状态（推荐）

完整历史仍永久保存，但每轮只发送 token 预算内的近期消息，并附带滚动摘要、开放话题、已回答问题、关系阶段、边界和最近关系事件。该方案能在成本可控的情况下保持连续性，也能让服务端规则明确表达不可重复事项。

### 方案 C：近期原文 + 摘要 + 选择性检索

在方案 B 之上按关键词或向量检索旧消息。长期可用于很长的关系历史，但需要新的索引、排序、隐私与误召回策略。Alpha 当前先不做，待方案 B 的回放集证明确有必要后再单独立项。

## 5. 推荐架构

### 5.1 权威事实层

现有 `messages` 表继续保存完整会话档案。只有状态为 `completed` 的用户/角色消息进入上下文；`withdrawn` 消息及其对应角色回复不得进入 provider、搜索、关系记忆或摘要。

用户消息可以在生成开始前持久化，但只有收到 provider `done` 并成功保存角色消息后，该轮才可触发长期记忆、话题状态和关系事件更新。失败、取消和未完成流不更新这些派生状态。

### 5.2 派生上下文层

新增一个 provider-neutral 的 `ConversationContextSnapshot`（名称可在实现阶段调整），由服务端读取和组装：

```ts
type ConversationContextSnapshot = {
  recentMessages: Array<{ role: "user" | "character"; content: string }>;
  rollingSummary: string | null;
  openTopics: Array<{
    topicKey: string;
    label: string;
    status: "open" | "answered" | "closed";
    lastMentionedBy: "user" | "character";
    lastMessageId: string;
    lastAnswer?: string;
  }>;
  characterClaims: Array<{
    claimKey: string;
    statement: string;
    assertedAt?: string;
    sameLocalDay?: boolean;
  }>;
  openCommitments: Array<{
    commitmentKey: string;
    owner: "user" | "character";
    statement: string;
    dueHint: "later-today" | "tomorrow" | "unspecified";
    status: "open";
    madeAt?: string;
  }>;
  relationship: {
    stage: "new_contact" | "getting_to_know_you" | "familiar" | "close_friend";
    summary: string | null;
    recentSignals: Array<"shared-detail" | "accepted-care" | "requested-space" | "repair-needed" | "affection-received">;
    boundaries: Array<"low-pressure" | "no-investigative-questions" | "slow-affection" | "no-real-world-claims">;
  };
};
```

现有 `ReplyContext` 保留 provider 所需的最终字段，并增加摘要和开放话题投影。`CharacterReplyProvider` 只依赖这个统一内部 DTO，不读取数据库，不知道具体 provider 名称。

### 5.3 近期上下文预算

第一阶段继续使用最近消息作为短期记忆，但将固定条数改成服务端 token/字符预算。默认目标是保留最近约 6–10 个完整来回，达到预算后从最旧消息开始裁剪。当前用户消息始终单独放在最新位置，不依赖它是否已经写入历史查询结果。

预算必须可配置并记录在内部算法版本中，不把 provider 的上下文窗口当成业务事实。未来 provider 更换时只调整 adapter 映射，不改关系数据。

近期消息保留可选的 `sentAt` ISO 时间戳。Lucía 的连续性判断以 `Europe/Madrid` 为默认会话时区，服务端计算 `currentLocalDate` 和话题的 `sameLocalDay`，但不把客户端本地时间当成关系事实。时间字段用于判断“今天稍早已经聊过”，不要求角色在回复中机械地报出时间。

### 5.4 滚动摘要

摘要只描述已经完成且允许共享给 Lucía 的会话事实，例如认识来源、反复出现的兴趣、最近聊过的生活主题和关系节奏。摘要不保存原始私密长文本，不替代消息档案。

摘要更新可以先采用确定性的服务端规则和有限模板；若后续使用模型压缩，模型输出必须经过 schema、长度、敏感级别和冲突检查，并作为候选而不是直接事实。摘要更新失败不能阻塞用户已经完成的回复，下次可重试。

### 5.5 开放话题与重复抑制

每个完整回合后，从用户消息和角色回复中提取有限的主题状态。第一阶段优先覆盖显式问答、日常报备和承诺事项，不做通用语义图谱。

规则示例：

- 若同一问题近期已被角色回答，则下一次生成上下文标记为 `answered`，提示 provider 不要重复相同答案。
- 若同一问题在当前本地日已经被回答，额外标记 `sameLocalDay`；生成结果与上一答案高度重复时，服务端最多触发一次“换新细节/自然承认前文”的重生成。
- 若用户重新提出相同主题，允许角色承认前面提过并提供新细节，不强迫使用“我记得”。
- 若角色曾提出问题但用户尚未回应，不自动再次追问；除非用户主动回到该话题。
- 开放话题有过期时间，过期后只作为弱参考，避免长期纠缠。

这层是“减少机械重复”的服务端信号，不是要求每次回复都显式提及记忆。

### 5.6 角色自述状态

用户问题的连续性之外，还要保留 Lucía 自己最近说过的短期日常事实。第一阶段从已完成的角色回复中确定性提取有限主题（例如当天饮食、饮品和精力状态），形成 `characterClaims` 投影。它不是人物圣经，也不是长期关系记忆；默认只在近期窗口和当前本地日内作为弱事实参考，并带有原始消息时间。

如果新回复提出与同日角色自述冲突的具体日常内容，服务端最多触发一次重生成，要求自然说明“改变了主意”或延续之前的说法。没有足够明确的主题值时不做强行判断，避免把正常的状态变化误判为矛盾。饮食、饮品等 `daily_observation` 是可重复的日常行为：跨到下一本地日后再次出现相同内容不构成矛盾，也不需要解释；`sameLocalDay=false` 时不触发该门禁。

### 5.7 关系状态注入

普通聊天 route 必须读取当前 Lucía contact/relationship 记录，把真实 `relationshipStage` 和西语 `relationshipSummary` 注入 `buildReplyContext`。没有记录时仍使用安全默认值，但 active Lucía 不得静默回退到 `new_contact`。

关系摘要和最近关系信号使用定性事实，不以单一好感度分数决定行为。关系阶段更新仍需独立的服务端规则和完整回合证据；本设计先消费已有状态，不在同一切片内重写阶段升级算法。

### 5.8 计划与未完成承诺

从完整消息中只提取用户或 Lucía 明确说出的短期承诺，以及用户明确说出的普通日常计划，例如“今晚告诉你考试结果”“之后给你发照片”“今天下午去港口拍照”。承诺带有拥有者、时间提示和状态：`open` 表示仍待完成，`returned` 表示用户已经说“回来了/结束了”。每条计划按消息时间/序号生成独立实例，即使两天都说“去港口拍照”也不会覆盖旧计划；返回信号只推进它之前最近的用户普通计划，不把无关的“今晚告诉你”承诺误判为已完成。它们作为低压力连续性线索；provider 不应每轮追问进度，计划也可以推迟、取消或自然失效。用户说“回来了/结束了”时，角色应从活动结束后的视角承接具体计划细节，而不是继续使用“祝你玩得开心/希望拍得愉快”一类事前表达，也不得凭空断言结果。第一阶段不把承诺写入长期关系记忆，取消/延期和更丰富的完成判定留待后续状态快照切片。

## 6. 生成与持久化流程

```text
请求到达
  ↓
读取关系、摘要、开放话题、近期完成消息和隐私过滤记忆
  ↓
加入当前用户消息，构建 ReplyContext
  ↓
调用 provider
  ↓
安全门禁；失败不 fallback、不写角色文本
  ↓
收到 done 后保存角色消息
  ↓
派生更新：记忆候选、开放话题、摘要、关系事件候选
```

任何派生更新都必须绑定 `generationId`/完整回合，重复请求不能重复生成或覆盖较新的快照。旧 generation 的回调不得更新当前状态。

## 7. Provider 提示边界

provider 的 system prompt 只说明如何表达：

- 先回应当前用户内容，再决定是否延续；
- 尊重 `questionPolicy` 和关系边界；
- 不重复 `answered` 话题的相同问答；
- 关系状态和开放话题是上下文事实，不要把内部字段说给用户；
- 用户未询问 AI 身份时不要主动插入身份声明，直接询问时如实回答。

服务端安全门禁继续负责身份声明、问题压力、产品化用词、虚构现实行动和其他硬不变量。提示词不是安全边界。

## 8. 错误、降级与隐私

- 历史、摘要或开放话题读取失败时，使用最小安全上下文继续请求；读取失败不能伪造记忆。
- provider 失败或安全门禁失败时不生成 fallback 角色文本，不保存完整助手消息，也不更新关系派生状态。
- 撤回消息在构建上下文前过滤；用户删除关系记忆后，后续上下文必须重新按权限读取。
- 日志只记录上下文版本、消息数量、摘要长度、topic 数量和关联 ID，不记录完整私密对话或摘要原文。

## 9. 测试与评测

第一阶段至少新增：

1. 上下文构建单元测试：近期消息预算、撤回过滤、当前消息注入、隐私记忆过滤。
2. 关系注入测试：active Lucía 的真实阶段和摘要进入普通聊天 provider input；无关系记录使用安全默认值。
3. 开放话题测试：已回答问题标记、未完成问题不重复追问、相同主题重新出现允许新角度。
4. 计划生命周期测试：用户在“今天下午去港口拍照”后发送“Ya he vuelto.” 时，最近普通计划变为 `returned`；provider 不得再输出事前祝愿语，而应承接已结束的活动或自然收束。
5. 对话路由集成测试：完整回合后才更新派生状态；失败/取消/旧 generation 不更新。
6. provider 契约测试：不同 provider 收到等价的 provider-neutral 字段，不把数据库类型泄漏到 adapter。
7. Lucía 回放集新增重复话题案例：
   - 已问过“中午吃什么”，再次询问；
   - 旧话题被自然重新提起；
   - 用户换话题后不强行拉回旧记忆；
   - 关系阶段从 `new_contact` 到 `familiar` 时表达强度有差异。

验收不要求两个 provider 生成相同句子，只比较连续性、重复率、关系边界、问题压力和事实一致性。

## 10. 分阶段实施

### 第一阶段（本次批准范围）

- 修复普通聊天的 Lucía 关系阶段/摘要注入。
- 提取 provider-neutral 上下文构建接口。
- 将近期上下文改为预算化，并增加开放话题的最小投影。
- 保留消息时间并加入同一本地日判断，防止日常话题在同一天被重置。
- 对同日同主题的高度重复答案执行一次服务端重生成。
- 提取 Lucía 的短期角色自述，并阻止同日具体日常事实被无解释地改写。
- 明确区分同日一致性和跨日可重复行为，避免把“今天吃土豆泥、明天又吃土豆泥”误判为冲突。
- 增加重复问答门禁/提示信号和固定回放测试。
- 保持现有消息表和 provider adapter 接口兼容。

### 第二阶段（后续单独确认）

- 滚动摘要持久化与重试。
- 关系事件候选和关系阶段更新规则。
- 更长历史的选择性检索。
- 跨设备同步和移动端共享同一上下文 DTO。

## 11. 验收标准

- 对话历史仍可完整恢复，撤回/删除语义不变。
- 普通聊天 provider input 不再默认使用 Lucía 的 `new_contact`，active 关系阶段和摘要可被验证。
- 回放集中重复午饭问题的重复回答率下降，且没有强制出现系统化“我记得”措辞。
- provider 切换不改变关系阶段、记忆权限和问题预算。
- 相关单元、集成、契约和回放测试通过；不调用真实收费 provider 作为默认测试。
